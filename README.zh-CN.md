# CommitGate（提交身份门）

> **状态：尚未发布。** 本仓库正在准备首次公开发布。只读、仅用标准库、不联网。

## 它为解决什么问题而存在

文件扫描器不会去读 git 的 author 字段。

一个仓库可以让内容扫描零命中，同时它的历史仍然写着究竟是谁提交的。这不是假设，是实测：
有一个公开仓库

- 12 个 commit 里有 6 个的 `author` 与 `committer` 都是某个私人身份，
- 另有 1 个是第二个私人身份，
- 5 个注解 tag 的 `tagger` 全部是同一个身份，

而同一棵树的文件内容与提交正文扫描都是零命中。那个仓库上的每一道门禁都在读文件。
没有一道读 author 字段，所以没有一道可能发现它。

两个性质让它不只是「不够整洁」：

- **改写历史修不掉。** 拉取请求的 head 引用（`refs/pull/2/head`）会让它指向的 commit
  在改写引入它的分支之后仍然可达。经由 PR 发布出去的泄漏，能活过对 `main` 的改写。
- **注解 tag 是第二个面。** tag 对象自带 `tagger` 身份。改写 commit 不会碰 tag 对象，
  所以一条干净的 `main` 仍然可能发布一个由错误的人签署的 tag。

唯一能拦住它的时刻是 **push 之前**。

## 它做什么

`commitgate` 读取仓库里的每一个 ref 与每一个可达 commit，报告其中 `author`、
`committer`、或注解 tag 的 `tagger` 不在你提供的允许名单上的那些；
并按可选的「内部上下文」正则扫描每一条提交正文。

```bash
python3 -m commitgate . --allow "你的名字 <you@users.noreply.github.com>"
```

在仓库根目录运行；包从源码导入，未安装。默认输出 Markdown，`--format json` 输出 JSON。

## 退出码

| 码 | 含义 |
|---:|---|
| `0` | 已产出报告，且只有 `info` 级发现 |
| `1` | 存在至少一条 error 或 warning，所以 **不要 push** |
| `2` | 仓库读不到，或策略缺失 |
| `3` | 报告已算出但写不进 `--output` |

`2` 与 `1` 分开是刻意的。「你的历史里有外部身份」和「这个工具根本没读成你的历史」
是两个不同的事实。把读失败当成干净结果的调用方，会发布一个它从没看过的身份 ——
那正是门禁绝不能产出的结果。

## 检查项

| 检查 | 报告什么 |
|---|---|
| `identity-author` | `author` 不在允许名单上的 commit |
| `identity-committer` | `committer` 不在允许名单上的 commit |
| `identity-tagger` | `tagger` 不在允许名单上的注解 tag |
| `commit-message` | 命中内部上下文正则的提交正文 |
| `reachability` | 总是报告读了多少 commit 与 ref |

最后一项不是客套。只说「零发现」而不说读了多大的报告，和「什么都没读」无法区分。

## 为什么 author 与 committer 分开查

不带 `--reset-author` 的 `git commit --amend` 会保留原来的 **author**，只重写
**committer**。只钉住两者之一的工具，仍然可能发布另一个。CommitGate 两个都查。

与之相关、自己写门禁时值得知道的一条：git 解析身份时，**先**读环境变量
`GIT_AUTHOR_NAME` / `GIT_COMMITTER_NAME`，**后**读 config 里的 `user.name`。
只传 `-c user.name=...` 挡不住继承来的环境变量；两个通道都要钉。

## 策略

`名字 <邮箱>` 对的允许名单，可用重复的 `--allow` 提供，也可用 `--policy` 指定一个文件：

```
# 允许的发布者
你的名字 <you@users.noreply.github.com>
```

没有「大概没问题」这一档。不在名单上的身份就是一条发现，因为这个工具要抓的失败
正是「作者没意识到自己被发布了出去」这种。

空策略会被直接拒绝，而不是对着空无一物报干净。

## 依赖

Python 3，仅标准库。无第三方包、不联网、不需要凭据、不需要数据库。
只有跑测试时才需要 `pytest`。

## 已验证

2026-10-10 实测，CPython 3.14.3：

- 14 条用例通过；
- 泄漏只挂在 `refs/pull/2/head` 上（此时 `main` 是干净的）时被报告、退 1；
- commit 全部干净、只有一个注解 tag 的 tagger 是外部身份时被报告、退 1；
- 泄漏在最旧一条提交正文里（其上还有 8 条干净 commit）时被报告，
  说明正文扫描不是一个「最近若干条」的窗口；
- 指向非仓库的目录退 2，不是 0；
- 发布树检查被埋入一个真实内部上下文词时会变红，移除后恢复绿色。

## 未验证

- **Python 3.8 与 3.12 本机没跑过。** 它们是 CI 矩阵覆盖的版本，而写这个包的机器上
  只有 3.14.3 与 3.9.6（后者没有 pytest）。在 CI 报告出来之前，
  「在 3.8 上可用」应视为未测。
- **没有对真实公开仓库跑过端到端。** 上面每一条都是为测试临时造的仓库。
- **不接触任何远端。** 本工具只读本地 ref。某个托管方会不会永久保留 `refs/pull/*`
  是托管行为，不是本工具能保证的事。

## 不包含

- 不改写历史。改写已发布历史属于仓库所有者的决定，而悄悄改写正是
  让一个泄漏变得无法挽回的方式。
- 不检查文件内容。那部分请用内容扫描器；本工具看的正是内容扫描器不看的那个字段。
- 不了解托管平台、账号或权限。
